Field Guide · Real examples

Agents in the wild

Everything in the guide, running in my actual setup. Real names, real files, real wiring, from a small three-person agent mesh I run across a couple of Discord servers and one Linux box.

Nothing exotic here. It's the same three parts (file, tools, loop) repeated, plus the git plumbing that lets separate accounts share one brain. Each example below points back at the section of the guide it makes concrete.

01

An agent really is one file

↔ Section 1

My little org (the "War Room") has five named agents. Each one is literally a single markdown file in a folder called agents/. Here's one, trimmed, exactly as it lives in the repo:

 warroom/agents/jane.md
# Jane, my personal agent

- Tier:    Internal (Claude)
- Owner:   me
- Runtime: Claude Code on my personal account

## Role
My side of the internal tier: personal assistant, builder,
driver of hands-on work across the repos. Pairs with Junior
(my partner's agent), one per owner, under the shared
secretary Nyx.

## Relationship to Nyx
Nyx is the always-on ambient daemon. Jane is me,
interactive, at the keyboard. Same brain files,
one writer, no forking a second source of truth.

That's the entire agent. Role, tier, which model runs it, who it pairs with. No framework, no magic. Change the file, change the agent.

02

The roster, and why model choice is a cost decision

↔ Section 1 & 4

Five files, five agents, two tiers. The split isn't about smarts, it's about who you trust with what, and who pays for it. Trusted internal work runs on the pricier Claude seats. The public-facing front-line bots run on a cheaper model through OpenRouter, kept off the Claude seats on purpose.

This is the "one file, one job" idea from the guide, five times over. The two axes that actually drive the design: trust (internal vs public) and cost (Claude vs cheaper external). Everything else is just prompt.

03

The loop, running by itself

↔ Section 3

Nyx isn't something I open and talk to. It's the loop from the guide, running unattended. A small Discord bot (built on the Agent SDK) bridges Discord to Claude Code: each time you @mention it, a thread opens that IS a live agent session, and each channel is pinned to a working directory (a repo) so the agent knows what it's looking at.

On top of that, a few scheduled runs give it a heartbeat. These are just the loop, kicked off by a timer instead of a message:

7:05am, Mon–FriMorning briefReads the board and the inbox, posts a summary to the team channel. Read-only.
2:00am, nightlyConnective-tissue passLinks today's items back to the past ("3rd time onboarding friction came up"), updates the memory files.
on every messagePromise-catcherHears a spoken commitment ("I'll ship X Friday") and quietly files it to the board with an owner and a soft due-date.

Same read → decide → act loop. I just don't have to be the one who presses go.

04

The hard part, solved with a git repo

↔ Section 5

This is the account-splitting problem from the guide, made real. Three agents on three different accounts (mine, my partner's, the shared secretary) need one shared brain without an always-on server or an open port. The answer turned out to be boring and bulletproof: they talk through a git repo.

Janemy account
Nyxshared, always on
Juniorpartner's account
↓   git pull / push   ↓
the shared repo = the brain + mailbox
todo.jsonBRAIN.mdDECISIONS.mdinbox/outbox/

Each agent clones the repo with its own token. A timer commits and pushes every ~10 minutes. No peer-to-peer, no inbound port, no live server, and because it's pure git it costs zero model tokens. One rule keeps the peace: only the secretary writes the board, so three agents never fight over the same file.

The memory files (BRAIN.md, DECISIONS.md) are exactly the "memory is just files" point from Section 1. The inbox/ and outbox/ folders are the whole messaging protocol. That's it. The hard part wasn't intelligence, it was picking a dumb, reliable pipe.

05

Who pays: the billing trap

↔ Section 5

The one that bites you in production.

An always-on agent that listens to every message can quietly burn through a shared plan's usage cap and take everything else down with it. The fix is unglamorous: the ambient secretary runs on a separate account, pinned with one environment variable (CLAUDE_CONFIG_DIR), so its usage never touches the shared seat. This is the "billing the wrong card" line from the guide, and it's the kind of thing no tutorial mentions until it's already cost you.

None of this is fancy. It's the guide's three parts (file, tools, loop) plus a git repo doing the talking and a couple of timers doing the nudging. If you can write a markdown file and run git push, you can build the whole thing. Start with one agent: back to the guide →
