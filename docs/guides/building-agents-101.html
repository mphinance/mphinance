Building Agents
the part nobody explains

You asked the right "dumb" question. It isn't dumb. Everyone glosses over this and then acts like the whole thing is magic. It's not.

An agent is a text file of instructions, plus a list of tools it's allowed to use, running in a loop against a model.

That's the whole thing. Three parts. Learn them and you can build anything you've watched me build.

01

The file IS the agent

You had it basically right. At the base level, yes, an agent is a markdown file. That file is the system prompt. It's the first thing the model reads before it does anything, and it's the only thing that makes "the market analyst" different from "the bug hunter." Same model underneath. Different file in front of it.

 quant-verifier.md
ROLEThe job. "You review Pine Script for correctness and math errors." One sentence, up top.
RULESThe guardrails. "Never suggest code you haven't read. Cite the line number. Flag bad math before saying anything nice."
PERSONAThe flavor. Blunt vs polite, terse vs chatty. Matters less than you'd think.
CONTEXTWhat it needs to do the job. File paths, house style, the definition of "done."

You wrote it as "rules and personality." I'd flip the weight:

Role first Rules second Personality, distant third

For TDPro I don't care if an agent is charming. I care that the quant-verifier catches a divide-by-zero before it ships. Role and rules do the work. Personality is seasoning. Your instinct, "their role affects how the prompts get written and what they go do," you nailed it and then talked yourself out of it. The role IS the prompt. There's no deeper layer hiding underneath.

And "memory"? Just more files. When an agent "remembers," it's reading a file of past notes, a rubric, prior corrections, before it starts. Same idea as the system prompt, one folder over.

02

Tools are how it touches the world

A model on its own can only produce text. It can't read your files, hit an API, or run code. Tools are what you hand it to reach outside the chat.

R

read_file

Give it a path → get the contents back. How Sam reads your trade log.

S

run_screener

Give it a ticker → get live flow data. The agent pulls before it answers.

W

write / deploy

Change a file, ship a build. Scoped to only the agents allowed to.

A tool is just a function with a name and a description. The model reads your descriptions, decides which one it needs, and calls it. You wire the code behind it. This is the whole difference between a chatbot and an agent: a chatbot talks; an agent talks, then does: reads, calls, writes, checks its own work.

Safety tip: you decide which tools each agent gets. The release-captain can deploy. The design-critic cannot. Scope tools to the role and that's most of your safety right there.

03

The loop is the engine

Here's the part that isn't in the file and isn't a tool, and it's why this felt "deeper than you thought." The agent runs in a loop:

1

Read

Everything so far: prompt + task + tool results.

→
2

Decide

Answer, or reach for a tool.

→
3

Act

Call the tool, run it.

→
4

Feed back

Push the result back into context.

↺  repeat until the job is actually done

That loop is what makes it feel alive. It's not one question, one answer. It's read → act → check → act again, until the thing is finished. You don't write the loop yourself for most setups. The framework runs it. But knowing it's there is the line between "I typed a prompt" and "I built an agent."

Each cell in that matrix is one agent's file pointed at one job. It's not 16 technologies. It's 16 markdown files and a router. The orchestrator is itself just an agent whose role happens to be traffic control. Turtles all the way down, and every turtle is the same three parts: file, tools, loop.

05

The genuinely hard part

It isn't the intelligence. It's the plumbing.

Everything above runs on a Claude account. The moment you want a shared agent that also talks to your personal one and my personal one, you've got three accounts that have to cooperate without stepping on each other or billing the wrong card.

Sharedours, the one we both use
Your personaltalks to the shared one
My personaltalks to the shared one

That's not an agent problem. It's identity, credentials, who-pays, who's-allowed-to-talk-to-who. It's the boring infrastructure part, and it's 80% of why a real multi-agent setup is real work while a single agent takes an afternoon. You were right to sense there was more. The "more" is wiring, not intelligence.

06

When to even build one

Before you build anything, run the job through four gates. Pass all four and it's worth automating. Miss one and you'll spend a weekend building something you have to babysit anyway.

1
Recurring?You do this again and again. A one-off isn't worth an agent.
2
Rule-governed?There's a right and wrong way, not pure taste.
3
Criteria you can name?If you can't write down what "good" looks like, the agent can't either.
4
Output verifiable?You can check whether it actually did the job.

Four yeses → build it.   One no → wait.

The clean version of this test comes from Karo and Dheeraj Sharma. Their line sticks: agentize the tasks, not the craft, and keep the human decision where judgment matters. Same thing I keep saying about my own writing, so it's not just me being precious.

Start here: do this today

Don't build the swarm. Build one agent and feel the loop. Make it a critic, it's the easiest first job and it teaches everything.

Write one markdown file.

Role: "You review my trade ideas and tell me what's wrong before what's right." Add 3 rules. Skip personality for now.

Give it one tool.

Read your trade log. Then lock permissions: read-only, plus one write path to a reviews/ folder. No deletes, no sending. That is the whole safety model at this stage.

Run it. Ask it something.

Watch it read the file, then answer. That moment, read then decide then act, is the click.
Once that clicks, the matrix stops looking scary. It's just that, sixteen times, with a router on top. That's the whole thing. Ask me anything on the call.
